## 3. تجربة الحساب: من التسجيل إلى التفعيل

### شاشة الدخول

- Username.
- Password مع زر إظهار/إخفاء.
- Save login / تذكر دخولي.
- زر دخول بحالات تحميل ونجاح وفشل واضحة.
- رابط إنشاء حساب وفق المسار النهائي، ورابط استعادة الوصول.
- دعم مدير كلمات المرور عبر autocomplete الصحيح، والسماح بلصق كلمات المرور.
- رسالة فشل عامة لا تكشف إن كان Username موجودًا.

### إنشاء الحساب — المسار المقترح

1. يختار العضو Username وكلمة مرور ويؤكدها.
2. يتحقق الخادم من صحة الاسم وعدم تكراره وقوة كلمة المرور، ويطبق حدود محاولات التسجيل.
3. ينشئ هوية مصادقة وحسابًا بحالة `pending`، دون رتبة أو صلاحيات يختارها العضو لنفسه.
4. يصل العضو بعد الدخول إلى صفحة «حسابك بانتظار الاعتماد» فقط.
5. يرى Admin Level 3 المخول الحساب في قائمة انتظار الاعتماد.
6. يتحقق من العضو ويربط الحساب بسجل عضو الفريق الصحيح، ويحدد الرتبة والاسم الظاهر والصلاحيات المسموحة.
7. يعتمد الحساب في عملية موثقة واحدة، فيصبح `active`.
8. تتحدث صفحة العضو عند إعادة تحميلها أو التحقق الدوري القصير، دون الحاجة لإنشاء حساب آخر.

لا يكفي تشابه الاسم لإثبات عضوية الفريق. يكون الربط بسجل عضو ذي معرف ثابت، بعد مراجعة المسؤول؛ ويُمنع ربط حسابين بالسجل نفسه دون إجراء نقل موثق.

| حالة الحساب | ما يراه | وصوله إلى بيانات الفريق |
|---|---|---|
| pending | حالة طلب الاعتماد ومعلومات حسابه الأساسية وتسجيل الخروج | ممنوع |
| active | الصفحات والبيانات المسموحة لدوره | حسب الصلاحيات |
| rejected | رسالة عدم اعتماد عامة وطريق مراجعة المسؤول | ممنوع |
| disabled | رسالة تعطيل الحساب وطريق مراجعة المسؤول | ممنوع؛ تُلغى جلساته |

حالة الحساب مستقلة عن حالة الإداري في اللعبة. الإداري الموقوف للتدريب قد يحتاج حسابًا فعالًا لرؤية حالته وتاريخه؛ إيقاف التدريب لا يعطل حساب الموقع تلقائيًا.

## 4. Username والاسم الظاهر والهوية

| الحقل | الاستخدام | قابل للتغيير؟ |
|---|---|---|
| user_id / staff_id | الربط الدائم للتقارير والطلبات والتدقيق | ثابت |
| username | تسجيل الدخول | ثابت في الواجهة المعتادة |
| username_normalized | منع التكرار والبحث الداخلي عن هوية الدخول | يشتق من Username |
| display_name | الاسم المعروض في الموقع | يغيره Admin Level 3 ضمن نطاقه، والمالك |
| game_rank | رتبة اللعبة وقواعد الأداء | تتغير بقرار مخول مع حفظ التاريخ |
| site_role / capabilities | حقوق الموقع | منفصلة عن رتبة اللعبة |

المقترح لاسم الدخول: 3–32 حرفًا من الحروف الإنجليزية والأرقام والنقطة والشرطة والشرطة السفلية؛ غير حساس لحالة الأحرف، مع رفض المسافات والأسماء المحجوزة. الاسم الظاهر يدعم العربية والإنجليزية، ويمكن ألا يكون فريدًا؛ معرف العضو هو أساس التمييز.

تغيير الاسم الظاهر يسجل من غيّره ومتى والقيمة السابقة والجديدة. لا تتغير كلمة المرور أو Username أو صاحب الإحصائيات أو التاريخ. لا يظهر Username ضمن قوائم الفريق العامة، ولا تستخدم الأسماء كمفاتيح لربط البيانات.

## 5. تنفيذ دخول Username بصورة سليمة

Supabase Auth يعتمد كلمة مرور مرتبطة ببريد أو هاتف. تصميم Username المطلوب يحتاج طبقة ربط إضافية؛ هذه ليست خاصية Username جاهزة في Supabase.

المعمارية المقترحة للتطبيق:

1. يحتفظ الخادم بربط خاص بين Username وهوية Supabase Auth، في مخطط بيانات غير مكشوف للمتصفح.
2. عند عدم طلب بريد من العضو، ينشئ الخادم عنوانًا تقنيًا فريدًا مشتقًا من معرف الحساب، لا من الاسم الظاهر، ويستخدمه داخليًا مع Supabase Auth. العنوان ليس بريدًا لاستقبال الرسائل.
3. عملية إنشاء الهوية وتأكيد عنوانها التقني تتم بخادم موثوق؛ التسجيل المباشر في Supabase يُغلق، ولا تُرسل رسائل تأكيد إلى عناوين تقنية.
4. يدخل العضو Username وكلمة المرور فقط. يحل الخادم الربط الداخلي ويطلب من Supabase Auth التحقق من كلمة المرور.
5. تُنشأ جلسة التطبيق بعد نجاح المصادقة؛ حالة العضوية وحقوقها تُفحص مستقلًا عنها.

العنوان التقني لا يحمي الحساب بمجرد كونه غير ظاهر. الحماية تعتمد على كلمة المرور، وحدود المحاولات، وحماية الجلسات، وسياسات البيانات. وجود هذا الربط يعني أن استعادة الوصول لا تستخدم بريدًا وهميًا.

إنشاء هوية Auth وسجل التطبيق عمليتان منفصلتان تقنيًا؛ يلزم مفتاح منع تكرار وتعويض عند الفشل، حتى لا يبقى حساب صالح بلا سجل عضوية. أي حساب غير مرتبط بحالة عضوية معروفة يفشل وصوله افتراضيًا.

### استعادة الوصول دون بريد إلزامي

- يسجل العضو طلب مساعدة عبر المسار المعتمد، وتكون رسائل الموقع عامة دون كشف وجود Username.
- يتحقق Admin Level 3 من هوية العضو من خلال إجراءات الفريق المعروفة قبل إصدار الاستعادة.
- يصدر رمز استعادة عشوائيًا، لمرة واحدة، محدود المدة، ولا تحفظ قيمته الأصلية في قاعدة البيانات.
- يفتح العضو المسار الخاص ويختار كلمة مرور جديدة بنفسه؛ لا يحتاج المسؤول إلى معرفة الكلمة الجديدة.
- يلزم تنفيذ الرمز واستهلاكه بطريقة تمنع الاستخدام المتزامن، مع سجل محاولة موثق وإلغاء جلسات الحساب السابقة.
- لا يستطيع Admin Level 3 استعادة حساب المالك أو حساب مسؤول خارج نطاقه. استعادة المالك لها مسار تشغيلي خاص موثق.
- إذا أُضيف بريد استعادة حقيقي مستقبلًا، يكون اختياريًا ومتحققًا منه، مع خدمة إرسال مناسبة؛ يتبعه تحديث صريح للخطة.

المقترح الأولي لكلمات المرور: حد أدنى 15 حرفًا عند عدم وجود تحقق ثنائي، ودعم كلمات مرور طويلة واللصق ومدير كلمات المرور. تُفحص القيم على الخادم، ولا تحفظ نصًا صريحًا في جداول التطبيق أو السجلات.

## 6. Save login وإدارة الجلسات

**المقترح:** جلسة تطبيق تديرها طبقة الخادم، مع Cookie عشوائية غير قابلة لقراءة JavaScript، وليست حفظًا لكلمة المرور.

| الحالة | السلوك المقترح |
|---|---|
| دون Save login | Cookie جلسة، مع انتهاء خادمي بحد أقصى 12 ساعة وخمول 60 دقيقة |
| مع Save login | الاحتفاظ بالدخول على الجهاز والمتصفح نفسيهما حتى 30 يومًا كحد أقصى؛ ينتهي عند خمول 7 أيام |
| تسجيل خروج | إلغاء جلسة الجهاز ومسح Cookie |
| خروج من كل الأجهزة | إلغاء جميع جلسات التطبيق وإبطال تجديد جلسات Auth ذات الصلة |
| تغيير كلمة المرور أو استعادتها | إلغاء الجلسات القديمة وإصدار جلسة جديدة بعد التحقق |
| تعطيل الحساب | منع الطلب التالي إلى البيانات وإلغاء جلسات التطبيق |
| تغيير الصلاحيات | تطبق الحقوق الجديدة على الطلب التالي، دون انتظار انتهاء JWT قديم |

هذه مدد مقترحة قابلة للتعديل في إعدادات السياسة بواسطة المالك. بعض المتصفحات تستعيد Cookies الجلسات بعد إعادة الفتح؛ لذلك لا يُعتمد على إغلاق المتصفح وحده لانتهاء الدخول. حذف Cookies، الوضع الخاص، تغيير الجهاز، أو انتهاء الجلسة قد يتطلب الدخول مرة أخرى.

تفاصيل التنفيذ:

- Cookie باسم خاص بالتطبيق وخصائص `HttpOnly` و`Secure` و`SameSite=Lax`، ومقيدة بالمضيف والمسار.
- يخزن الخادم بصمة معرف الجلسة، وتواريخها وحالة الإلغاء. تُشفّر رموز Auth اللازمة للتجديد بمفتاح مستقل محفوظ ضمن أسرار الاستضافة.
- جميع طلبات بيانات التطبيق تمر عبر الخادم؛ لا يعتمد هذا التصميم على عميل Supabase Auth داخل المتصفح.
- القراءة والكتابة المعتادة تستخدم هوية العضو ورمزه الموثق لتطبيق RLS؛ المفتاح السري الإداري يقتصر على عمليات مثل تهيئة الهوية وإدارة مخزن الجلسات الخاص.
- تربط جلسة التطبيق بمعرف جلسة Auth؛ تتحقق سياسات البيانات من حالة العضوية ومن وجود جلسة تطبيق صالحة توافق `session_id` داخل الرمز الموثق، عبر وظيفة محدودة لا تكشف مخزن الجلسات. هكذا يعمل الإلغاء والانتهاء على الوصول الفعلي أيضًا، مع اختبار JWT صالح توقيعيًا لكن جلسة تطبيقه ملغاة.
- يُفصل العميل الإداري عن العميل الخاص بكل مستخدم، ويُمنع الاشتراك في عميل خادمي عالمي ذي جلسة قابلة للتبديل بين الزوار.
- تجديد الرموز له قفل أو آلية منع تعارض بين الطلبات، لأن Refresh Tokens تتغير.
- تُحمى الطلبات التي تغيّر البيانات من CSRF، ويُمنع تخزين الصفحات أو الردود الشخصية في Cache مشتركة.
- الوظائف الحساسة، ومنها منح الصلاحيات والاستعادة والتصدير الواسع، تحتاج إعادة تحقق حديثة من كلمة المرور.
- لا تحفظ كلمات المرور أو رموز الدخول في localStorage أو تقارير الأخطاء أو ملفات GitHub.

التحكم المقترح في مدد جلسة التطبيق مستقل عن خيارات انتهاء جلسات Supabase المتاحة في الخطط المدفوعة. لا نفترض توفر ميزة مدفوعة ضمن المجاني، ولا ندعي أن ضبط Max-Age وحده يلغي جلسة Auth.

| تغيير إعدادات حساسة للنظام | لا | لا | بتفويض محدود | بتفويض محدود | نعم |

تُعتمد `approve_accounts` لـAdmin Level 3 الذي يعيّنه المالك، ثم يمكن تفويضها لمسؤول مناسب. لا يستطيع المسؤول ترقية نفسه أو تعديل Owner أو منح حقوق تتجاوز نطاقه. تثبيت أول مالك وأول مسؤول معتمد يتم بإجراء إعداد واحد محدود وموثق، لا بزر متاح للعامة.

سياسة نشر الإحصائيات تجمع ثلاثة شروط: الحساب فعال، العضو مرتبط بسجل فريق صحيح، والرتبة الموثقة إحدى Moderator/Administrator/Responsible. لا يستطيع أي Grant أو دور Owner تجاوز منع Helper وSN.Helper.

تظل «متابعتي» و«إدارة الفريق» محور التنقل. تظهر الأدوات الإضافية لمن يحتاجها، مع استخدام الحوارات والتفاصيل المنظمة. لا توجد قائمة لتبديل الدور يدويًا في المنتج الحقيقي؛ هذه كانت وظيفة معاينة فقط.

لا يضاف بحث عام يشوش الواجهة. توجد تصفية محلية عند الحاجة، مثل البحث عن عضو داخل شاشة إدخال الإحصائيات أو الحسابات.

- توقيت التشغيل: `Asia/Riyadh`؛ تخزن اللحظات بالتوقيت العالمي UTC وتعرض وفق المنطقة.
- الأسبوع: الاثنين 03:00 فجرًا حتى الاثنين التالي 03:00 ؛ البداية مشمولة والنهاية غير مشمولة.
- الاجتماع: الاثنين 22:00 بتوقيت السعودية، والحضور يشمل المجاز إلا بتبرير مقبول.
- الفلاجات تراكمية؛ 7–9 متابعة مع Moderator، و 10 فأكثر مسار إيقاف للتدريب واعتماد العودة. لا تتصفّر أسبوعيًا.
- الفلاجات الواردة في لقطة تقرير ليست زيادة جديدة تلقائيًا؛ تمنع مضاعفة الواقعة بين التقرير وسجل الانضباط.
- كل تحذيرين = توبيخ، وكل ثلاثة توبيخات = مسار فصل بقرار موثق. تُسجل الوحدات المستهلكة في التحويل لمنع إعادة احتسابها.
- الإيقاف للتدريب والفصل والإنذار حالات مختلفة. تنفيذ قرار في اللعبة يبقى للمسؤول المخول خارج الموقع حتى يتوفر تكامل معتمد.
- الإجازة لا تخفض أهداف الأسبوع.
- التبرير يُقدم قبل المناوبة بأكثر من ساعة، مع بديل مقبول يغطي المناوبة.
- للعضو الجديد سياسة يوم إجازة بعد مرور 14 يومًا ضمن الشهر الأول؛ يجب مطابقة تطبيقها مع تاريخ الانضمام عند الاستيراد.
- الرصيد يتجدد بشهر تقويمي جديد دون حذف الطلبات القديمة. لا يشترط فتح الموقع عند بداية الشهر ليتجدد.
- تعديل الرتبة أثناء الفترة لا يعيد كتابة الماضي؛ يحتفظ كل تقييم بإصدار السياسة والرتبة المؤثرة، وتوثق سياسة احتساب الفترة الانتقالية قبل تشغيل تغيير منتصف الأسبوع.

### مصدر كل رقم

كل تقرير مرتبط بالعضو والفترة ووقت القياس ونوع المصدر ومن أدخله. التذاكر التراكمية والساعات الأسبوعية والتقييم لقطات أو ملخصات معتمدة، وتُعرّف طريقة جمع كل حقل صراحةً. لا تُجمع لقطات تراكمية، ولا يضاف الملخص الأسبوعي إلى اليومي مرة ثانية، ولا يؤخذ متوسط تقييمات بلا أساس معتمد.

البيانات الناقصة تظهر «لم تُضف» وتختلف عن صفر حقيقي. يذكر الملخص عدد الأعضاء المحدثين، ويُسمى الإنجاز المجمع «الإنجاز المسجل» عند نقص البيانات. النسب التي تتجاوز 100% تبقى ظاهرة دون تشويه طول مؤشر التقدم.

العدد الحالي للأعضاء ونسب النموذج في المعاينة ليست حقائق تشغيلية؛ المصدر الحقيقي هو البيانات المدققة عند الاستيراد.

تضاف مفاتيح خارجية، وقيود فريدة، وحقول `created_at` و`updated_at` و`created_by` المناسبة، ومراجعات لمنع التعديل المتزامن. لا تعتمد الاستعلامات على حقل غير موجود في جدول أو View. يبنى مخطط موثق وأنواع TypeScript من المخطط نفسه، وتختبر الاستعلامات فعليًا.

الوظائف التي تحتاج أكثر من تعديل، مثل اعتماد حساب ومنحه رتبة أو حجز رصيد، تنفذ معاملات ذرية. تمنع سباقات طلبين يتجاوزان الرصيد باستخدام قفل السجل أو إجراء آمن مكافئ.

Views المستخدمة في العرض تحترم RLS وهوية المستعلم؛ لا تمنح صلاحية مالك قاعدة البيانات تلقائيًا. وظائف `security definer` تقتصر على الضروري مع مسار أسماء ثابت وصلاحيات تشغيل محدودة، وتعيد التحقق من هوية الفاعل ونطاقه.

## 11. الاستيراد والبيانات الحقيقية

1. تحليل ملفات الأعضاء والإحصائيات والسياسات، وتحديد تاريخ كل مصدر وصحته دون تحميل أسرار إلى الكود.
2. استيراد قائمة الفريق إلى منطقة مراجعة، مع معرف ثابت للعضو وربط الحسابات لاحقًا.
3. تحويل التواريخ بتفسير صريح للتنسيق والمنطقة الزمنية؛ تظهر القيمة الأصلية والقيمة المفسرة للمراجع.
4. قراءة Excel في نطاقه الصحيح مع رفض الملفات غير المدعومة أو الكبيرة وإبقاء صيغها كنص عند الحاجة، دون تشغيل أكواد أو ماكرو.
5. مطابقة الأعضاء بمعرفات موثوقة. تشابه أسماء العرض يولد حالة تحتاج مراجعة، ولا يُدمج تلقائيًا.
6. تحديد اللقطات التراكمية والنتائج الأسبوعية والوقائع المنفصلة قبل احتساب الأرقام.
7. عرض معاينة: جديد، تحديث، تكرار، تعارض، مرفوض، وأسباب الرفض.
8. استخدام بصمة الملف ومفاتيح فريدة للسجلات لمنع إعادة إدخال الدفعة نفسها.
9. اعتماد الدفعة المخولة، مع تقرير نتائج لكل صف؛ لا تعني رسالة نجاح عامة أن كل الصفوف مقبولة.
10. التصحيح بإصدار جديد أو عكس دفعة محددة موثقًا، مع حفظ المصدر والتاريخ.

المرفقات في حاويات خاصة وروابط عرض محدودة الصلاحية. يرتبط الملف بسجل ومستحقين واضحين، وتمنع سياسات Storage الوصول إلى مرفقات الغير. تراجع نوعية الملف الفعلية وحجمه، وتعرض الملفات غير الآمنة للتصفح كتَنْزيل لا محتوى نشط.

## 12. الهيكل البرمجي والتسليم

```text
app/                 صفحات Next.js ومسارات الخادم
components/          عناصر العرض المشتركة والمتخصصة
features/            الحسابات، الفريق، الإحصائيات، الطلبات، الانضباط
lib/auth/            ربط Username والجلسات والاستعادة
lib/permissions/     تعريف القدرات وفحص نطاقها
lib/db/              عميل المستخدم والعميل الإداري المنفصل
lib/domain/          الفترات والأهداف والأرصدة والقواعد
lib/validation/      مخططات التحقق المشتركة
styles/              متغيرات الهوية والأنماط
public/assets/       الشعارات والخطوط وخلفية المدينة
supabase/migrations/ إنشاء المخطط وتطويره بالتسلسل
supabase/tests/      اختبارات SQL والصلاحيات والمعاملات
tests/               اختبارات القواعد والتكامل والواجهة
scripts/             الإعداد والاستيراد والنسخ الاحتياطي
docs/                المتطلبات ومصفوفة الحقوق ودليل التشغيل
```

التسليم النهائي يشمل مصدر المشروع وملف قفل الاعتمادات وملف `.env.example` دون قيم سرية وMigrations ودليل الإعداد والنشر والنسخ الاحتياطي وتقرير الاختبارات وحدودها. ZIP المصدر للتسليم لا يحتوي `.env` أو كلمات مرور أو مفاتيح أو نسخ بيانات شخصية.

الأسرار مثل مفتاح Supabase الإداري ومفتاح تشفير الجلسات تحفظ في بيئة الخادم. لا تستخدم بادئة `NEXT_PUBLIC_` لأي سر. لا تُحفظ بيانات تشغيل حقيقية ضمن Fixtures أو سجل المستودع.

## 13. مراحل التنفيذ وبوابات الانتقال

| المرحلة | العمل | نتيجة قابلة للمراجعة ومعيار انتقال |
|---|---|---|
| 0 — تهيئة | تثبيت مسار إنشاء الحساب، إنشاء مصدر جديد، اختيار الإصدارات والأصول وبيئة البيانات | مشروع منظم يبني بنجاح وخطة صلاحيات ثابتة |

| 3 — الواجهتان | نقل التصميم المعتمد، متابعتي وإدارة الفريق، الحالات الفارغة والنقص والتحميل | شكل معتمد على الشاشات المستهدفة دون بيانات مزيفة في الإنتاج |

## 14. خطة الاختبار والقبول

### الحسابات والجلسات

- Username غير حساس لحالة الأحرف، والاسم المكرر مرفوض دون إنشاء هويتين.
- كلمة مرور خاطئة وUsername غير موجود يولدان ردًا عامًا، مع حدود محاولات فعالة عبر أكثر من نسخة خادم.
- الحساب Pending لا يقرأ بيانات فريق عبر الصفحة أو API أو اتصال قاعدة البيانات.
- العضو لا يستطيع اعتماد نفسه أو اختيار رتبته بإرسال قيم معدلة.
- Admin Level 3 المخول يعتمد حسابًا ضمن نطاقه؛ Moderator لا يفعل ذلك.
- اعتماد متزامن وربط عضو مستخدم مسبقًا لا يولدان روابط مزدوجة.
- الاسم الظاهر يتغير، والدخول يظل بالـUsername نفسه، والتاريخ مرتبط بالمعرف الأصلي.
- مع Save login يستمر الدخول بعد إعادة فتح المتصفح؛ دون الخيار تطبق حدود الجلسة المقررة.
- انتهاء الجلسة وإعادة التجديد وفتح عدة تبويبات لا تسبب تبادل حسابات أو تعارض رموز.
- تعطيل الحساب أو خفض حقوقه يمنع الطلب التالي حتى مع JWT لم ينتهِ.
- إلغاء جلسة التطبيق أو انتهاء مدتها يمنع قراءة البيانات برمز Auth قديم لم تنتهِ صلاحيته التوقيعية.
- الخروج من الجهاز أو من كل الأجهزة يعمل وفق الخيار، والاستعادة تلغي الجلسات القديمة.
- رمز الاستعادة لا يعمل مرتين ولا بعد انتهاء مدته، ولا يسمح باستهداف حساب أعلى صلاحية.

### الصلاحيات والخصوصية

- Helper وSN.Helper يفشلان في نشر الإحصائيات حتى بطلب API مباشر أو Grant إداري.
- Moderator فعال يستطيع نشر تقرير صحيح دون امتلاك إدارة الفريق تلقائيًا.
- سحب رتبة Moderator يوقف النشر فورًا وفق قواعد التحقق المقررة.
- تغيير `staff_id` أو معرف طلب أو ملف إلى معرف عضو آخر لا يتجاوز الحق الممنوح.
- لا يستطيع Admin Level 3 منح Owner أو تعديل نفسه أو حساب أعلى من نطاقه.
- المرفق الخاص لا يصبح متاحًا بتغيير الرابط أو معرفة اسم الملف.
- لا تحتوي الردود على أسرار الدخول أو تفاصيل لا يحتاجها الدور، ولا تسرب Cache بيانات بين مستخدمين.

### القواعد والبيانات

- اختبار اللحظة السابقة لبداية الأسبوع واللحظة المطابقة لها والنهاية غير المشمولة.
- التواريخ المعكوسة أو الغامضة لا تستورد بتخمين صامت.
- نقص البيانات مختلف عن صفر، ولا يجمع الإجمالي التراكمي مرتين.
- إعادة إرسال التقرير أو الملف نفسه لا تضاعف التذاكر أو الفلاجات.
- حدود التقييم 4.80 و 4.85 ، والفلاجات 6/7/9/10 ، تعمل كما هو معتمد.
- تجديد الرصيد الشهري ينجح دون Job إجباري لحظة منتصف الليل، ويحتفظ بالماضي.
- طلبان متزامنان لا يتجاوزان الرصيد، ورفض الطلب يعكس الحجز مرة واحدة.
- التبرير عند ساعة بالضبط يُعامل وفق قاعدة «أكثر من ساعة»، والبديل المقبول شرط مستقل.
- سياسة العضو الجديد وتغيير الرتبة والتاريخ القديم تختبر كل منها بحالات واضحة.
- قرارات التدريب والعودة لا تحذف الفلاجات ولا تنفذ تغييرًا غير مخول في اللعبة.

### الواجهة والتشغيل

- العربية وRTL والأسماء الطويلة والجداول والنوافذ تعمل عند 320/375/390/430/768/1024/1440 بكسل.
- فحص Safari على iPhone وChrome على Android، والكمبيوتر والتابلت، مع تجربة جهاز فعلية قبل الاعتماد.
- لوحة مفاتيح وتركيز واضح وتسمية الأزرار وإغلاق الحوارات واستعادة التركيز وتباين مقروء.
- حالات فارغة وتحميل وفشل شبكة ورفض صلاحية ومحاولة مكررة، دون فقد مدخلات النموذج.
- الملفات والصور والخطوط محسّنة، وتحترم الواجهة تفضيل تقليل الحركة.
- `typecheck` وBuild واختبارات القواعد والتكامل والصلاحيات ناجحة على نفس المصدر المنشور.
- تجربة نسخة احتياطية واستعادتها قبل الاعتماد، وتقرير بما تم اختباره فعليًا وحدوده.

## 15. الرفع والنشر ومسار الرجوع

1. مصدر GitHub جديد خاص، بفرع تطوير و`main` للإصدار المعتمد، مع حماية الدمج بحسب ما تسمح به خطة الحساب.
2. مراجعة تغييرات المصدر وMigrations وتشغيل الفحوص قبل الدمج؛ لا تحفظ أسرار داخل المستودع.
3. ربط GitHub بـVercel وضبط متغيرات كل بيئة، مع عنوان معاينة مختلف عن الإنتاج.
4. قاعدة اختبار منفصلة عن البيانات الحقيقية. يمكن استخدام Supabase محليًا في التطوير، ومشروع اختبار سحابي عند توفره ضمن خطة الحساب. لا نفترض توفر عدد غير محدود من المشاريع المجانية.
5. مرحلة التجربة السحابية الجديدة تستخدم حسابات اختبار وبيانات واضحة المصدر قبل الاستيراد الفعلي. بعد تحول المشروع الجديد إلى إنتاج، لا يعود Preview متصلًا به باعتباره قاعدة اختبار.
6. النسخة القديمة تظل محفوظة للمرجع وخطة الرجوع؛ لا يُنفذ حذف أو استبدال بياناتها تلقائيًا.
7. قبل نقل المستخدمين: أخذ نسخة بيانات ومرفقات وإعدادات، وتوثيق SHA وإصدار المخطط، واختبار الاستعادة.
8. تطبيق Migrations على قاعدة جديدة أو معتمدة، ثم إعداد المالك والحسابات المعتمدة واستيراد البيانات المقبولة.
9. نشر الإصدار وربط عنوان ثابت، ثم اختبار الدخول والجلسات وصلاحيات الأدوار والبيانات على العنوان الحقيقي.
10. عند نجاح الاعتماد، توثيق رابط التشغيل ودليل المسؤول والاستيراد والاستعادة وإدارة الأرصدة.

**الرجوع:** الرجوع إلى Deployment قديم لا يعكس تغيير قاعدة البيانات تلقائيًا. تعتمد الخطة تغييرات مخطط متوافقة قدر الإمكان، ونسخًا احتياطية، وخطوات استعادة بيانات مستقلة. إلغاء نشر إصدار أو تراجع الكود لا يُستخدم كبديل لاستعادة قاعدة سليمة.

### المجاني والاستمرارية

الخطة الأساسية تستهدف استخدام الحدود المجانية دون اشتراك إجباري. Vercel Hobby مشروط بالاستخدام الشخصي غير التجاري؛ يجب أن تتوافق طبيعة استخدام الموقع معه. Supabase المجاني له حدود وقد يتوقف عند قلة النشاط، ولا نفترض نسخًا احتياطية مدفوعة أو سجل استعادة لحظي ضمنه. تُعد خطة نسخ احتياطي خاصة بالمشروع، مع مراقبة الاستخدام.

إذا تعارضت شروط الحساب أو حدود الخدمة مع الاستخدام المطلوب، يراجع بديل الاستضافة قبل الإطلاق دون شراء تلقائي أو وعد باستضافة مجانية غير محدودة. دومين مخصص ليس شرطًا للبدء؛ يمكن اعتماد الرابط المجاني أولًا، وتحديد الدومين لاحقًا.

## 16. ما يؤجل حتى يستقر النظام الأساسي

- Discord Bot وحساب التذاكر من رسائل done، إلى مرحلة تكامل مستقلة بصلاحيات وقنوات مؤكدة.
- تسجيل الدخول بديسكورد لا يدخل هذا الإصدار؛ الدخول المطلوب Username/Password.
- دليل عقوبات اللاعبين حتى تحديد نسخة مرجعية معتمدة؛ يبقى منفصلًا عن انضباط الإداريين.
- أي أتمتة تغيّر صلاحيات اللعبة أو ترسل رسائل إلى الآخرين حتى يحدد المستخدم نطاقها ومصدرها.
- التحليلات المعقدة وميزات إضافية لا تخدم تشغيل الواجهتين والحسابات والبيانات الأساسية.

## 17. المطلوب للبدء والعناصر التي يمكن تنفيذها فورًا

**يمكن بدء المصدر والمكونات والمخطط والاختبارات محليًا بناءً على هذه الخطة، دون الحاجة إلى ZIP القديم.** الملفات القديمة تصبح مدخلات مراجعة واستيراد عند الوصول إليها.

| المدخل | متى يلزم؟ |
|---|---|
| تثبيت من ينشئ الحساب: العضو أم Admin Level 3 | قبل إنهاء مسار التسجيل |
| تحديد حساب أول مالك وأول Admin Level 3 وربطهما بعضويتهما | عند إعداد بيئة التشغيل؛ لا تكتب كلمات مرور في الشات |
| GitHub وVercel ومشروع Supabase جديد أو بيئة مخصصة | عند مزامنة المصدر والتجربة والنشر |
| ملفات الفريق والإحصائيات الحالية المعتمدة | قبل الاستيراد الحقيقي |
| سياسة أرصدة القيادة وتغيير الرتبة منتصف الفترة | قبل تشغيل هذين المسارين، وليس قبل بناء الأساس |
| قناة تحقق هوية العضو والاستعادة | قبل إتاحة الاستعادة للمستخدمين |
| رابط التشغيل النهائي والدومين إن وجد | عند النشر النهائي |

لا يحتاج المستخدم لإرسال مفاتيح سرية أو كلمات مرور هنا. تهيأ في أدوات الخدمات أو متغيرات الخادم المعتمدة عند مرحلة الإعداد.

**أول جزء تنفيذي:** أساس المشروع والمخطط والصلاحيات، ثم تجربة كاملة لحساب جديد يدخل بـUsername وكلمة مرور، ينتظر الاعتماد، يعتمد بواسطة Admin Level 3 ، يتغير اسمه الظاهر، ثم يعود عبر Save login إلى مساحة صحيحة الصلاحيات.

## 18. مراجع تقنية تم التحقق منها

هذه المصادر تثبت سلوك الخدمات؛ التفاصيل الخاصة بربط Username وجلسة التطبيق وحالات الاعتماد قرارات معمارية مقترحة لهذه الخطة، وليست خصائص تلقائية توفرها الخدمات.

- [Supabase: Password-based Auth](https://supabase.com/docs/guides/auth/passwords) — معرفات المصادقة الأصلية بالبريد أو الهاتف.

- [Supabase: User sessions](https://supabase.com/docs/guides/auth/sessions) — رموز الجلسات وقيود التحكم المتاحة حسب الخطة.
- [Supabase: SSR advanced guide](https://supabase.com/docs/guides/auth/server-side/advanced-guide) — سلوك الرموز وتجديدها والفرق عن جلسة التطبيق المقترحة.
- [Supabase: Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security) — حقوق السجلات مع هوية المستخدم.
- [OWASP: Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) — ممارسات الدخول والاستعادة والتحقق.
- [OWASP: Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) — ضوابط Cookie والجلسات.
- [Vercel: Git deployments](https://vercel.com/docs/git) — معاينات الفروع ونشر الإنتاج.
- [Vercel: Hobby plan](https://vercel.com/docs/plans/hobby) — شروط الاستخدام المجاني.
- [Supabase: Free project pausing](https://supabase.com/docs/guides/platform/free-project-pausing) — قيود الاستمرارية في المجاني.

## 19. تعليمات استخدام الخطة في التنفيذ

ابدأ من المصدر الجديد مع نقل الأصول والتصميم المعتمد، وطبّق القرارات الأحدث أعلاه. نفذ المراحل بالترتيب، مع نتيجة قابلة للتجربة ومعيار قبول لكل مرحلة. حدّث حالة الاختبارات بصدق، وميّز بين ما هو مقترح وما نُفذ وما جُرّب فعليًا. لا تحمل أرقام المعاينة إلى إنتاج، ولا تكشف بيانات الفريق في رابط مراجعة مفتوح. لا تمنح حق نشر الإحصائيات لـHelper أوSN.Helper، ولا تخلط الاسم الظاهر بـUsername، ولا تخلط مصادقة الحساب باعتماد عضويته. احتفظ بخطة رجوع للمصدر والبيانات كل منهما على حدة.
